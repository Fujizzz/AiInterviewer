# Planner 输入精简与重规划调度

Planner 只生成考察目标、优先级和深度，QuestionAgent 生成具体问题。本次优化不改变完成判定、证据保存、质量检查和安全上限的职责。

## 模型输入与输出

`agents/planning/payload.py` 从持久化上下文生成专用视图：岗位要求、项目名称与领域、简短项目事实、所有可选话题，以及未关闭目标的完成状态、剩余缺口、被阻塞的信息需求、预算和已提问次数。最多发送最近三次回答的分析摘要；不发送完整简历、回答原文、评分、证据原文或逐条证据引用。文本摘要由程序生成，不增加模型调用。缺口和阻塞需求摘要带有总数，摘要截断不代表已完成。

完整上下文继续用于出题、审核、分析和报告。原有 `planning_view` 继续供 QuestionAgent 使用。

`CompactPlanProposal` 只需返回话题 ID、权重、深度、目标变更标记和简短原因。沿用目标时无需再次生成目标文本和完成标准；控制器恢复原有精确文本与证据。新增或明确替换目标必须提供完整的新目标与完成标准。项目归属由程序解析，模型不能自行指定。未知 ID、已关闭目标、过期版本、问题文本和预算字段会被拒绝。持久化记录仍使用原有 `PlanProposal`，旧记录保持可读。

## 重规划调度

普通话题预算耗尽、整体预算偏移和话题完成，使用本地分配器重新编译已有优先级，不直接触发模型调用。重要矛盾、明显的回答速度变化、议程无可执行目标和定期复核仍可请求语义重规划。局部失败的换题和恢复逻辑继续有效。

默认配置：超时仍为 30 秒；模型请求至少间隔两题；通常每四题复核一次；估计回答速度相对上次请求变化至少 35% 时可提前复核。议程耗尽可提前请求。程序每题仍更新实际时间和覆盖状态，不必等到定期复核。

后台仍只允许一个规划任务，不阻塞可执行的旧计划；接受结果时重新校验版本、目标状态和实际时间。模型请求的题号与速度基准单独持久化，本地预算调整不会重置其冷却计数。这两个字段位于现有 JSON 上下文中，本次没有新增数据库迁移。

## 目标保留与末题时间规则

初始规划中的 `objective_change=replace` 是创建目标时的一次操作。本地预算调整和失败后的备用规划会将沿用目标明确标记为 `preserve`，保留目标版本、完成条件、覆盖证据及信息缺口 ID；本地接受路径也不允许替换已有目标。模型明确提出的语义目标替换仍能创建新版本并撤下旧覆盖。

时长控制的是能否开始下一题。`planning.question_start_cutoff_seconds` 默认为 30：剩余大于 30 秒可以继续提问，剩余小于等于 30 秒不再发新题。接近结束、预计完整轮次无法放入剩余预算时，本地分配器释放收尾和机动预留，为一个末题目标分配实际剩余时间，不再因完整轮次估计提前结束。普通阶段仍使用完整轮次估计分配目标预算。

新话题、追问、故障恢复和出题完成后的检查采用同一时间门槛。因此 15 分钟配置下，14:20 可以继续提问，14:40 不再出新题；已经发出的题目允许回答跨过 15:00，保存并处理该回答后结束。若出题尚未完成就已进入最后 30 秒，不再发布该题。时间、题数安全上限以及无可用话题等终止条件继续由控制器判断，不依赖评分。

这两处修复通过 144 项直接相关 Agent 回归测试及 9 项后端回答完成测试，包含初始 `replace` 的本地复用、失败规划的证据保留、未提问目标的有效缺口、30/31/40 秒边界、出题跨入最后 30 秒、末题回答超过配置时长及重复提交。Ruff 与 `git diff --check` 通过；本次没有重跑完整测试套件或真实 API 面试。

## 2026-10-10 验证

对之前 15 分钟测试的五份规划状态进行同状态输入比较：首次请求从 10,579 字符降到 5,593 字符，减少 47.13%；四份重规划请求减少 69.93%～73.57%。字符数不等于 token 数，且不包含系统提示和 JSON Schema。

153 项直接相关 Agent 测试和 11 项后端回答推进、终止及报告安全测试通过。测试包括新目标、目标替换、证据保留、无效输出、超时备用规划、预算耗尽、冷却状态重载和后台过期结果处理。

真实 API 对照共请求五次，旧、新请求都收到 HTTP 404。新版三次尝试均进入本地备用规划；这不能证明模型正常响应时的耗时或规划质量改善。API 可用后需要再次做相同状态的少量对照，而不是把备用规划耗时当作正常模型生成耗时。结果保存在 `output/compact_planner_20261010T082120Z`。
