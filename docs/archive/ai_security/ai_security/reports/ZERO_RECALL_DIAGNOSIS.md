# 规则基线零召回：原因诊断

> 历史诊断：本文记录移除规则模式之前的实现、复测及当时建议；文中的“当前”均指诊断时版本。
> 随后按用户要求删除了文本规则及无模型路径。本文保留作为证据，不是现行配置或开发计划。

日期：2026-09-26。此次只诊断，不修改代码、表达式、策略阈值、标签、数据划分或原评测报告。

## 结论

主要原因是初版的检测实现只有六个狭窄的字面规则，没有接入语义模型，也没有实现上下文或行为
关联检测。公开集的攻击没有满足这些表达式，因此程序按既定逻辑全部返回 allow。
这是检测能力不足，不是有效防护；接口测试通过不能说明攻击识别目标已达成。

没有发现导致该零召回的下载损坏、标签反转、漏跑检查、预处理失真或混淆矩阵计算错误。

## 排查证据

1. 本地 Parquet SHA-256 与固定报告一致；benchmark、engine、rules、policy、共享契约五个
   源文件的 SHA-256 也均与报告一致，排除拿错版本复现。
2. 原始 test 数据有 116 条：label=1 为 60 条，label=0 为 56 条，无空文本；长度为 16–632
   字符，远低于本次显式扫描上限 100000，因此不存在超长截断或容量拒绝造成的指标混淆。
3. 发布者的[模型配置](https://huggingface.co/deepset/deberta-v3-base-injection/raw/main/config.json)
   明确 `0=LEGIT`、`1=INJECTION`，与本地评测一致。
4. 对全部样本直接逐条执行六个正则：原文命中数全部为 0，归一化文本命中数也全部为 0。
   因此不是下游把已检测的攻击错误变成放行。
5. 重跑原 evaluate 路径，仍得到 TP=0、TN=56、FP=0、FN=60、errors=0。
6. 独立追加诊断控制输入（不加入原数据或原报告）：两条明确英文覆盖/索取指令、一条中文
   满分操纵指令和一条正常描述，得到 TP=3、TN=1、FP=0、FN=0。说明调用和计数路径确实工作。

## 规则为什么漏检

### 固定词序和词表

英文覆盖规则要求依次出现：

```text
ignore/disregard/forget/override
→ 70 字符内 previous/prior/above/system/earlier
→ 35 字符内 instruction(s)/rule(s)/prompt(s)
```

在 60 条攻击中，仅 12 条含第一组动词；只有 2 条还满足第二组词及距离；最后完整命中为 0。
这些是只读的子条件统计，不是新规则，也没有拿它们替代原评测标准。

两条进入第二组条件但最终失败的具体记录（原序零基索引）：

- row 16：使用 previous orders，但名词词表没有 orders。
- row 15：后一处 above 到 instructions 之间相隔 39 字符，超过固定的 35 字符上限；
  前一处相隔 96 字符。表达明确的规则覆盖仍因表达式距离限制漏检。

### 提示词索取只接受三种固定对象

英文索取规则要求指定动词后接 system prompt、hidden instructions 或 internal rubric。
row 3、12 等记录改用“上面的提示内容”“所有提示文本”等说法，便不满足这一条件。
还有校对后复述、返回内部表示等方式，也未实现对应检测。

### 多语种、角色诱导和目标改变不在规则覆盖内

逐条查看攻击文本，可见英语、德语、西班牙语及混合语言；攻击文本中没有中文字符，三条中文
规则没有覆盖机会。原实现没有德语/西班牙语、拼写扰动、角色诱导、伪装正常任务等检测逻辑。

同源公开说明确认，数据集有语言翻译及正常内容与攻击内容叠加的构造：
[deepset 数据集介绍](https://haystack.deepset.ai/blog/how-to-prevent-prompt-injections)。
这与六条字面表达式所覆盖的范围明显不同，但不能归咎于数据集“太难”。

### 语义层没有实际运行

评测策略明确为 `rules_only`，benchmark 也拒绝其他模式。没有真实 LLM 或分类模型参与。
JsonSemanticReviewer 是供应商无关的生成接口适配器，模拟测试只验证结果校验和错误处理，
并不证明具备语义识别能力。没有规则命中时就放行，是当前配置的行为，不是检测异常后的回退。

## 数据适配与测试盲点

该公开二分类数据只提供 text/label，没有逐条绑定当前系统的可信任务、身份和会话上下文。
例如部分“扮演面试官”或“生成数据库代码”的记录标为攻击，在本系统的某些合法任务中可能
属于正常请求。原标签仍被完整保留；这是业务外推限制，不能用来解释掉那些明确覆盖指令的漏检。

当前安全单元测试主要验证已知模式与接口边界；它们大量使用规则本来能命中的短句，不能提供
独立泛化证据。合成场景中 TP=9、FP=3、FN=7 的结果也表明同时存在漏检和引用误报。

## 后续改进方向（本次未执行）

- 保留确定性权限、动作白名单、资源准入等硬约束。
- 将语义检测端口接入真实分类模型或 LLM，先在独立开发数据上验证，不假定接入即可有效。
- 构建包含任务上下文的中英文面试样本，特别包含安全讨论、引用攻击等困难负例。
- 固定模型、提示词、阈值和测试集，分别比较规则、语义及组合模式的召回、误报和业务影响。
- 此测试集已被逐条查看，不再称其为未接触的盲测；后续独立泛化评估需要新的未见数据。

仅把 35 改大或补几个同义词，可能修补个别漏检，但无法解决根本的语义与上下文缺失。
