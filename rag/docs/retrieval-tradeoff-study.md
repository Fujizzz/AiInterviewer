> **更正（2026-10-17）：第 1–4 节的延迟数字不代表团队仓库/服务器的实际配置。** 本研究用开发目录的检索代码，当时开发库的规划器走的是 HNSW 近似索引，所以 dense 只要 4–6 ms。团队仓库（及服务器）默认 `exact_dense=True`，走精确扫描，实测（团队代码 + int8 编码器，同一批 40 条查询，nDCG 0.602，与本研究一致）：
>
> | 环境 | dense 阶段 | lexical 阶段 | 端到端 p50 / p95（含编码） |
> |---|---|---|---|
> | 开发机，PG17，4 核 | 约 210 ms | 约 180 ms | 约 300 / 800 ms |
> | 服务器规格容器，PG14，2 核 / 1.5 GB / shared_buffers 768 MB | 约 400 ms | 约 190 ms | 约 510 / 1060–1360 ms |
> | 同上，1 核 / 700 MB / shared_buffers 256 MB | — | — | 约 830 / 1590 ms |
>
> 完整的服务器规格矩阵见第 1 节。因此：(1) "dense 比 hybrid 快两个数量级、延迟敏感场景改用 dense"不成立——精确搜索下 dense 本身就约 200–400 ms，hybrid 只比 dense 多 lexical 那约 180 ms（约 1.5–2 倍）；(2) 关键词上限 6 只影响 lexical 那一段；(3) nDCG 的结论不受影响（精确与近似的 nDCG 相差 0.002）。
> 服务器上端到端 p95 约 1–1.4 s，离 Agent 的 2 s 超时余量不大；可行的降延迟办法：dense 与 lexical 并行执行（总时间取较大者而非相加，约省 180 ms）。未实施。

## 1. 结论（推荐配置）

**hybrid（dense + lexical，RRF 融合），lexical 关键词上限 6，每路候选 top_n = 50，不开 rerank。服务器至少给 PG 2 核 / 1.5 GB（规格 A）；规格 B（1 核 / 700 MB）不建议。**

下表是**团队仓库代码的实际配置**（精确 dense 搜索 + int8 编码器，每次调用都真实编码，单位 ms，包含编码约 15 ms；40 条 gold v2 查询，每条跑 2 次取中位数）：

| 配置 | nDCG@10 | Recall@10 | 开发机 p50 / p95 | 服务器 A p50 / p95 | 服务器 B p50 / p95 |
|---|---|---|---|---|---|
| dense only | 0.578 | 0.601 | 198 / 227 | 431 / 483 | 514 / 556 |
| lexical only (cap 6) | 0.417 | 0.427 | 84 / 532 | 88 / 549 | 134 / 820 |
| hybrid cap 12, n 50 (old default) | 0.602 | 0.634 | 282 / 766 | 573 / 1248 | 964 / 2194 |
| **hybrid cap 6, n 50 (recommended)** | 0.599 | 0.631 | 283 / 758 | 340 / 805 | 999 / 1830 |
| hybrid cap 4, n 50 | 0.588 | 0.625 | 278 / 768 | 319 / 744 | 952 / 1532 |
| hybrid cap 6, n 20 | 0.594 | 0.625 | 286 / 799 | 338 / 1349 | 932 / 1720 |

- 服务器 A = PG14 容器 2 核 / 1.5 GB / `shared_buffers` 768 MB；服务器 B = 1 核 / 700 MB / 256 MB。均为本机 arm 上的 Docker，**x86 服务器未测**。
- 推荐配置 nDCG 0.599，服务器 A 上 p50 约 340 ms、p95 约 800 ms，服务器 B 上 p95 约 1.8 s，已逼近 Agent 的 2 s 超时。
- 延迟有噪声：每条查询只跑 2 次，且按顺序跑，同一环境内数据库缓存会越跑越热（例如服务器 A 上 hybrid 比先跑的 dense 还快），p95 在不同次运行里可差 30–60%。**只有数量级和大趋势可信**，例如不要把"上限 12 的 p95 1248 ms 对上限 6 的 805 ms"当成确定的收益；在开发机上这两者几乎相同（766 对 758 ms）。
- nDCG 在三个环境里完全一致（只取决于代码和语料）。

理由：LLM 生成本身要数秒，hybrid 比 dense 多出的约 100–300 ms 对出题/评分场景感觉不到；比 dense 的 nDCG 高 0.021（0.599 对 0.578）；rerank 在服务器上没有 torch，根本不可用。
例外：若某环节要在实时对话里每轮都调 RAG，可用 dense（nDCG 0.578，服务器 A 上 p50 约 430 ms、p95 约 480 ms；精确搜索下它比 hybrid 只快约 1.3–2 倍，不是之前误以为的两个数量级）。

## 2. 测试方法

- 脚本：`ndcg_latency_study.py`（开发目录里的一次性脚本，**不在仓库内**；它测的是 HNSW 近似 dense，数字已被第 1 节的矩阵取代）。每个配置对 40 条查询各跑 3 次取中位数。
- 延迟 = 数据库查询 + 融合（+ rerank），**不含** query embedding（bge-m3，约 20 ms/条，另计，需加到每一行）。查询向量已缓存。
- 对基线 `hybrid 上限12 n50`（修改前的线上配置）做配对 bootstrap 95% CI（10,000 次重抽样查询）。
- 变量：模式（dense / lexical / hybrid）、lexical OR 关键词上限（12/8/6/4/3）、top_n（50/20）、HNSW ef_search（100/40）、rerank 前 N（5/10/20）。

## 4. 发现

1. **hybrid 比 dense 略好，但差距不再显著**：+0.028，CI 含 0。代价是耗时从约 6 ms 到约 530 ms (p95)。慢的部分全在 lexical 那一路。
2. **OR 上限 12→6 几乎无损**（-0.001），**但没有提速**（p95 531 vs 530 ms）。第一轮（金标准 v1）里的"677→576 ms"是测量波动，不应当作优化收益。选 6 的理由只是"不降质量、查询更简单"。
3. **上限 4 以下开始掉分**，且 p95 反而更高（692 ms）。
4. **top_n 50→20 掉约 0.015**，耗时没有改善，保持 50。
5. **ef_search 100→40 掉约 0.012**，只省不到 1 ms，保持 100。
6. **rerank**：rerank10 的 nDCG 高 0.017，CI [-0.028, +0.068] 含 0，不能证明有收益；p95 涨到约 1.1 秒；rerank20 更差。当前不开。
7. **p95 的长尾（约 530 ms）靠调上限/top_n 解决不了**，原因是 lexical 的 OR 查询会命中大量行再打分；需要改查询本身（例如先用 GIN 取候选再排序），本次未做。

## 5. 为什么 nDCG 从 0.60 降到 0.52，又回到 0.60

| 条件 | hybrid nDCG@10 |
|---|---|
| 搜原 22 个源（16k 块），金标准 v1 | 0.601 |
| 搜全部 246 个源（95k 块），金标准 v1 | 0.522 |
| 搜全部 246 个源（95k 块），金标准 v2（补标） | 0.605 |

- v1 金标准只标了原 22 个源里的相关块。语料扩到 246 个源后，新增源里同样好的答案（如 Wikipedia 的一致性哈希、PEFT 文档的 LoRA 说明）排进前 10，却被算作"错"，所以 0.522 是**低估**。
- 对前 10 名里 149 个"新增源但未标注"的位置，人工（我）看标题和开头文字，约 40% 实际相关（清单由 `rag.eval.studies.unlabeled_top10_review` 生成）。据此补了 17 条查询的规则（`data/eval/gold_extra_labels.yaml`），合并为 `data/eval/gold_queries_v2.yaml`。
- 复现（仓库内）：`python -m rag.eval.studies.unlabeled_top10_review`（导出未标注命中）、`python -m rag.eval.studies.build_gold_v2`（合并规则，规则在 `rag/data/eval/gold_extra_labels.yaml`）。范围对照（只搜原 22 个源）是开发目录里的一次性脚本，不在仓库内。

## 6. 局限

- **v2 标注是草稿**：根据检索结果的标题/开头写成，有轻微循环论证；部分规则偏宽（g10、g11、g16、g31、g32 各新增 20 多个块），会抬高所有配置的绝对分数，对配置间比较影响较小。需要人工抽查。
- 只补标了 17 条查询；原 22 个源里的 154 个未标注命中没看。
- 40 条查询统计功效低，"CI 含 0"表示未证明有差异，不是没有差异。
- 真实短板不在标注：释义改写类（g27 到 g30）、配置项（g17、g18）、面试题（g34 到 g37）查询在前 10 名里几乎没有相关结果。
- 延迟在本机 (Mac, colima 4 vCPU/6 GB) 上测得；目标服务器 2 vCPU / 3.5 GB，绝对值会不同，需要部署后复测。

## 8. 追加：冷门词查询的融合修复与置信度重新校准（2026-10-16）

**现象**：队友发现 TeaCache 查询返回了 PagedAttention 内容且置信度为 medium。随后用 62 个自拟技术词复测，发现 HyperLogLog（库中 15 块）、CORS preflight（17 块）在 hybrid 前 10 名里一条都没有，而单跑 lexical 能全部命中。
**原因**：dense 遇到不认识的词会返回一堆"向量相近但无关"的块；融合时 dense 权重是 lexical 的 2 倍（RRF 权重 2.0、k=10），dense 前 5 名的得分都高于 lexical 第 1 名，把正确答案挤出前 10。置信度只看 dense 相似度，且阈值 0.52 是 16k 语料时标定的，扩到 95k 后负样本只能识别 14/22。

**改动**（`rag/retrieval/retriever.py`、`confidence.py`；评测 `python -m rag.eval.studies.fusion_fix_eval`）：
1. **自适应融合**：lexical 逐字命中代码式标识符、且 dense 最高相似度 < 0.62 时，lexical 的 RRF 权重 1→3；另外当 dense 最高 < 0.50 且有"全词命中"时也提权（针对 CORS 这类缩写）。
2. **缺失标识符判低**：查询里有不含连字符的代码式标识符（TeaCache），而全库没有任何块逐字包含它时，置信度判 low。
3. **阈值**：`dense_low` 0.52→0.55；标识符逐字命中时只有 dense < 0.45 才判 low（单个冷门标识符的 dense 本来就低，不能因此判 low）。

**验证**（金标准 v2 + 120 个从语料自动抽取的冷门标识符，seed 0，另含 15 个编造名和 22 条负样本）：

| | 改动前 | 改动后 |
|---|---|---|
| gold v2 nDCG@10 | 0.604 | **0.604**（不变） |
| 标识符切片 nDCG@10 | 0.554 | 0.604 |
| 冷门标识符 hit@10 | 78/120 | **117/120** |
| 编造名判 low | 9/15 | **15/15** |
| 负样本判 low | 14/22 | 18/22 |
| 答得出的查询被误判 low | gold 0/40，冷门词 3/120 | gold 0/40，冷门词 0/120 |

被否决的方案：不加 dense 条件直接提权，冷门词 120/120，但 gold nDCG 掉 0.022（PostgreSQL、FastAPI 这类常见标识符把 dense 的好结果挤下去）；"全词命中"也触发提权，gold 掉 0.07。
**局限**：`dense_low` 与 0.62 的阈值是在同一批 gold/负样本上调的，需要 held-out 复核；CORS preflight 这类"库里有、但 dense 极低且无标识符"的查询，排序已正确，置信度仍会是 low；团队仓库 `AiInterviewer/rag` 里的拷贝尚未同步这些改动。
